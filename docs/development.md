# OASIS 项目开发文档

**Othello Arena for Search and Interactive Self-play**  
版本 0.1 · 2026-11-18 · 开发计划

## 1. 项目目标与当前基础

OASIS 有两条并行主线。研究线在黑白棋上复现 RGSC，比较它与 AlphaZero 的样本效率和棋力，并通过组件消融、超参数实验和局面分析检验其机制。工程线提供浏览器人机对战和 AI 对战观战，最终用 Docker Compose 部署到 Linux 服务器。

当前项目已具备 AlphaZero-General 的黑白棋规则、MCTS、PyTorch 策略和价值网络、训练循环及命令行对弈。实际实现位于 othello/、search/、training/、models/、agents/ 和 scripts/。现有命令支持 6×6 和 8×8，随机及贪心玩家可作为初期联调和回归基线。下文的 RGSC、Web API 和部署配置是拟开发内容。

**首版范围**采用 6×6 快速验证、8×8 主实验与网页演示。论文使用 MiniZero、10×10 棋盘、三块残差网络和每步 200 次 MCTS 模拟。OASIS 的 8×8 结果用于回答相同预算下 RGSC 在本项目中的表现。若获得足够算力，再按作者 10×10 配置运行论文设置下的对照并单独报告。作者官方实现要求 Linux 和 NVIDIA GPU，论文给出的单次完整训练量级约为 150 个 RTX A6000 GPU 小时。 [论文 §4.2](https://openreview.net/forum?id=Eoiu5iJD71) · [作者代码与配置](https://github.com/rlglab/rgsc)

## 2. 研究线

### 2.1 实现顺序

1. **固定 AlphaZero 基线。** 归档当前代码版本。把随机种子、网络参数、训练预算和评估预算纳入配置。在 training/coach.py 中增加按真实自博弈步数收集样本的模式，并按固定预算导出评估检查点。保留 scripts/train.py 供回归验证。AlphaZero 和 RGSC 实验使用相同的策略／价值主干、棋盘表示、初始化协议、候选更新规则与 MCTS 预算。
2. **先接通局面重启。** 自博弈支持从合法的非终局局面开始，保存棋盘、真实执棋方和来源。记录实际被选中动作的 MCTS 价值、落子或跳过及终局结果。按双方视角对齐后，计算从当前状态到终局的后续估值误差，用于生成轨迹上的 regret 标签。用黑方胜、白方胜、和棋、单方无合法落点时跳过及双方均无合法落点时终局的样例核对标签与状态转换。
3. **实现完整 RGSC。** 增加 regret 数值头与排序头，按论文公式实现标签和排序损失。在 MCTS 节点扩展处采集可重启的候选局面，与实际自博弈轨迹一起参与候选排序。实际轨迹上的候选使用计算出的 regret，纯搜索节点使用数值头估计。优先缓存 PRB 保留高 regret 局面。普通开局生成入池候选，从 PRB 重启的对局结束后用指数移动平均更新重启局面的权重。记录来源、采样次数、棋局阶段、更新前后 regret 与移出原因。 [论文 §3 与附录 B](https://openreview.net/pdf/9ce57a6595e439b24df1da335e7ebcde6d554667.pdf)
4. **导出网页可用的模型。** 交付模型权重和清单，清单包含 `model_id`、算法、网络结构版本、棋盘尺寸、训练步数和权重校验值。AlphaZero 与 RGSC 通过同一玩家接口供竞技场与 Web 服务调用。首版的 regret 头用于训练时的重启选择，在线对弈统一从标准开局开始，落子沿用策略头、价值头和 MCTS。

### 2.2 实验矩阵与公平性

| 优先级 | 实验组 | 要回答的问题 |
| --- | --- | --- |
| 必做 | AlphaZero、完整 RGSC | 等样本预算下，RGSC 能否更快提升棋力？相同墙钟时间下是否仍有收益？ |
| 必做 | PRB 均匀重启 | 沿用完整 RGSC 的入池规则、容量和重启概率，仅把池内采样改为均匀分布。优先采样带来多少额外收益？ |
| 必做 | 去排序头、仅轨迹来源 | 分别用 regret 数值头替代排序打分，以及关闭纯 MCTS 节点来源。排序学习和搜索树候选各有什么贡献？ |
| 次要 | 随机、贪心、带棋盘启发式的 Alpha-Beta | 为训练曲线和网页提供可解释的棋力参照。传统搜索记录深度、访问节点或耗时 |
| 扩展 | 无 regret 的轨迹均匀重启 / Go-Exploit GEVC | 前者用固定容量队列保存历史轨迹局面并均匀重启，估计重启本身的作用。后者按原方法实现以对齐论文基线 |

- **训练预算**以对称增强前的真实自博弈根局面数为主口径，同时记录优化步数、采样量、墙钟时间和硬件。RGSC 从中盘重启，平均每局步数会变化，因此现有按局数运行的配置只用于快速验证。报告等样本曲线和等时间曲线，清楚标注两种比较的预算口径。
- **对弈预算**在相同棋盘、相同每步模拟次数和同一组评估开局下比较模型。每个开局交换执黑／执白，评估局面与调参局面预先固定。报告胜／平／负、得分率 `(胜局 + 0.5 × 平局) / 总局数` 及区间估计。Elo 曲线使用冻结的 AlphaZero 检查点作共同锚点，另报告两模型直接交手的结果。
- **重复与归档**建议主比较和关键消融至少用 3 个配对种子，报告各种子结果与汇总。对局区间按开局对或训练种子等实际独立单元估计。每次运行保存提交号、完整配置、种子、软硬件环境、检查点、原始对局记录和作图命令。按预先约定的训练步数选检查点，最终测试集用于报告。

### 2.3 超参数与机制分析

从论文推荐值开始，每次只改变一个参数。小预算先筛选，随后用相同主实验预算和多种子复测最有影响的设置。记录基准配置与所有候选的原始结果。 [论文附录 D](https://openreview.net/pdf/9ce57a6595e439b24df1da335e7ebcde6d554667.pdf)

| 参数 | 起点 | 扫描值 | 同时观察 |
| --- | --- | --- | --- |
| PRB 重启概率 λ | 0.5 | 0.2、0.5、0.9 | 标准开局覆盖、平均每局长度 |
| PRB 采样温度 τ | 0.1 | 0.1、0.5、1.0 | 采样集中度、不同局面的覆盖 |
| PRB 容量 κ | 100 | 100、500、1000 | 局面多样性和缓存周转 |
| EMA 更新系数 α | 0.5 | 0.1、0.5、1.0 | 同一局面被重访后的 regret 变化 |

机制分析安排三个可检验的问题。

1. **采到了什么？** 比较 RGSC 与均匀重启的采样分布，按剩余空格数或局面阶段分组，统计轨迹／搜索节点来源、唯一局面数和采样集中度。
2. **重访后是否改进？** 固定一批高 regret 局面及阶段匹配的对照局面，跟踪首次入池和后续重访的原始估值误差、EMA 记录及对固定对手的得分率。同步记录出池的局面，避免只看仍在池内的样本。
3. **能否迁移？** 用训练前冻结的独立局面集评估，按早中残局、角点争夺和强制跳过等局面分组。可对少量低空格残局用精确搜索验证关键落子。把训练中重访局面的改善和未作为重启目标的局面表现一同报告。

## 3. 网页与部署

建议采用 **FastAPI + React/TypeScript（Vite）+ Docker Compose**。FastAPI 复用 Python 棋盘规则和模型包装，前端负责显示与输入。首版通过 REST 提交落子和拉取状态，AI 对战按顺序返回可回放棋谱。生产环境由 Caddy 提供静态页面和 HTTPS，同一域名下的 `/api` 转发至 Python 服务。 [FastAPI 文档](https://fastapi.tiangolo.com/) · [Vite 文档](https://vite.dev/guide/) · [Caddy HTTPS 文档](https://caddyserver.com/docs/automatic-https)

### 3.1 对局流程与接口

- **人机对战。** 选择 AI 模型与执棋颜色。显示实时棋盘、合法落点、当前执棋方、棋子数、最后落点和胜平负。无合法落点时由服务端处理跳过，并把事件写入棋谱。AI 思考期间显示状态并禁用落子。
- **AI 对战。** 独立选择黑白双方模型和允许的搜索档位。服务器逐步生成棋谱，页面可暂停播放、单步前后查看并从最后收到的步数继续拉取。暂停控制本地播放，后台计算继续。
- **共用规则。** 服务端是棋局状态的来源。棋盘按行列序列化，`1` 为黑、`-1` 为白、`0` 为空。落子动作编码为 `row * board_size + col`，跳过编码为 `board_size²`。每条棋谱记录含连续步号、行动方、动作和落子后的状态。终局结果显式区分黑胜、白胜、平局。

| 端点 | 内容 |
| --- | --- |
| `GET /api/models` | 返回可用模型、棋盘尺寸、结构版本和允许的搜索档位 |
| `POST /api/games` | 根据模式、棋盘大小、双方模型或人类席位创建棋局。人机模式下向创建者返回落子凭证 |
| `GET /api/games/{id}` | 返回局面、合法动作、轮到哪方、局面版本、任务状态和结果 |
| `POST /api/games/{id}/moves` | 校验落子凭证，接收 `action` 与预期局面版本。拒绝非法动作、越权回合和过期提交 |
| `GET /api/games/{id}/moves?after_step=…` | 返回指定步数以后的棋谱，供轮询和回放 |

后端负责串行推进单局，针对每局建立独立 MCTS 树，已加载的推理权重按模型版本缓存。AI 计算进入有并发上限的后台队列，HTTP 请求只读写对局状态。首版可用一个服务进程和 SQLite 持久化棋谱。重启后保留已提交步数，对中途停止的任务标记中断并在页面展示。模型注册表由服务端维护，客户端提交模型 ID。

### 3.2 Docker 发布与验收

训练在开发机或训练服务器运行。线上 Compose 运行 `web`（Caddy 与前端静态文件）和 `api`（规则、对局与推理）。权重和模型清单按版本只读挂载，SQLite 使用持久卷。先在目标服务器实测 CPU 单步延迟和并发，再确定搜索档位及是否需要 GPU。保留镜像标签和对应权重检验值，支持成对回退。 [Docker Compose 生产部署文档](https://docs.docker.com/compose/how-tos/production/)

发布验收包括空白环境启动、健康检查、外网 HTTPS 访问、人机完整对局、两个不同模型完整对局与回放、强制跳过及平局、过期落子拒绝、服务重启后棋谱查询、镜像与模型版本回退演练。交付服务器部署说明、启动和日志命令、所需环境变量和发布版本清单。

## 4. 三人分工

| 工位 | 独立负责 | 首批可交接产物 | 最终验收 |
| --- | --- | --- | --- |
| A · 算法与训练 | RGSC 复现、重启路径、regret 标签及两类头、PRB、训练配置和消融运行 | 论文与代码映射、训练日志样例、6×6 最小配置、可加载的试验权重 | 复现代码、8×8 主模型、消融配置与运行记录 |
| B · 对局服务与评估 | 共用玩家接口、模型注册与加载、Arena 批量评估、Web API。制定评估口径并汇总结果 | API 契约、模拟 JSON、可运行的随机／贪心 API、评估开局与记录格式 | 两种对局 API、评估脚本、棋力结果和可复查对局 |
| C · 前端与部署 | 棋盘交互、AI 观战和回放、前端测试、Docker Compose、服务器发布 | 使用模拟数据的棋盘页面、镜像构建和测试环境 | 可访问的发布页面、端到端验收记录和部署说明 |

这个划分让 A 专注算法与算力，C 可以用模拟数据先做交互。B 把评估和在线推理依赖的玩家适配器做成共用接口。第三阶段的批量实验与机制分析由 A 主跑，B 负责核对指标和汇总，避免 B 同时承担全部实验与后端集成。A 与 B 共同核对棋盘及权重兼容，B 与 C 共同确认 API 契约与回放顺序。

## 5. 并行里程碑

以下以四周为排期模板。完整训练所需时间在 6×6 验证后根据实测吞吐和可用算力修订。

| 阶段 | A · 算法 | B · 服务与评估 | C · 前端与部署 | 进入下一阶段的条件 |
| --- | --- | --- | --- | --- |
| 第 1 周 · 约定接口 | 跑通 6×6 AlphaZero，测步数吞吐，确认 RGSC 标签与样本字段 | 固定玩家接口、评估配置和 API 模拟响应 | 用模拟数据完成选模型与棋盘页面 | 三人确认动作编码、模型清单、API 与实验日志格式 |
| 第 2 周 · 最小闭环 | 跑通 RGSC 的采样、重启、训练、导出 | 完成随机／贪心 API 与批量评估，加载试验权重 | 联调人机落子及 AI 对战回放，构建容器 | 6×6 两种算法都能导出并评估，网页两种模式能走完整局 |
| 第 3 周 · 主实验与集成 | 启动 8×8 主对照、重点消融与局面日志分析 | 固定评估开局，生成阶段曲线，调试队列和重启行为 | 在目标服务器上演练发布、HTTPS 与回放测试 | 至少一组 8×8 配对结果可复查，测试环境可从镜像部署 |
| 第 4 周 · 收尾发布 | 补关键种子，落盘权重、配置和研究结论 | 冻结结果与模型清单，复核胜平负和样本预算 | 发布版本、完成端到端验收和回退演练 | 提交可复现实验记录、可访问网页、镜像版本及部署说明 |

若算力低于预期，优先完成 8×8 的 AlphaZero、RGSC 和均匀重启对照，并提交趋势与不确定性。扩展基线、完整参数网格和 10×10 论文设置复现按剩余算力推进。网页可先使用随机、贪心和早期模型联调，最终发布时再替换为已核验的模型版本。
